Engineering lessons
Telemetry blind spot

The first test did not generate Event ID 4698. I traced the miss to Windows audit policy, enabled the required subcategory, verified the event locally, and reran the simulation.

Lab reliability

PowerShell execution policy and Defender quarantine interfered with Atomic Red Team setup. I corrected the isolated lab configuration rather than treating tool execution as proof that detection worked.

SIEM operations

Wazuh storage pressure exposed an infrastructure constraint. Vulnerability-detection data was disabled for this focused lab after diagnosing the disk issue.

Key takeaway

A rule cannot detect telemetry the endpoint never records. Audit-policy and sensor validation are part of detection engineering, not setup trivia.

Detection logic — generalized YARA rule
rule NSIS_Downloader_DisguisedMasquerading
{
  strings:
    $nsis_manifest = "Nullsoft.NSIS.exehead" ascii
    $version_info = "VS_VERSION_INFO" wide
    $version_generic = "FileDescription" wide
  condition:
    uint16(0) == 0x5A4D and
    $nsis_manifest and
    1 of ($version_info, $version_generic)
}
Engineering lessons
Rule overfitting

v1 matched only the sample it was written against. Generalizing to structural characteristics (NSIS manifest + PE version metadata) instead of exact strings brought it to 3/3 across unrelated malware families.

MAX_PATH limitation

Splunk's legacy "Run a script" alert action embeds the full SPL query and dispatch path into the script's command line, which breaks on Windows. Solved by building a custom JSON-over-stdin alert action instead.

Remote response

WinRM-based PowerShell remoting between the host and the VM was set up and confirmed reliable for automated kill-process and isolate-host actions.

Key takeaway

A rule tuned to one sample proves nothing about the technique. Generalizing against unrelated, related-family samples is what makes an IOC-based detection operationally useful.
