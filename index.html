CASE-01 · SOC-MONITORINGhigh volume

SOC Monitoring, Intrusion Detection & Digital Evidence Collection

Full attack-chain visibility — from first foothold to command and control.

Objective

Most training labs focus on spotting a single alert. I wanted to practice the harder skill: reconstructing an entire attack chain across nine tactics, from initial access through C2, the way an analyst would during a real incident.

Approach
  1. Deployed Wazuh agents and Sysmon across lab endpoints for process, network, and registry-level telemetry, forwarding everything into Splunk as the central SIEM.
  2. Built and tuned correlation searches around specific TTPs (credential dumping, suspicious PowerShell, SMB-based lateral movement) instead of relying on default, noisy alerting.
  3. Triaged 150–250 generated alerts by severity, manually validating true vs. false positives and preserving evidence for each confirmed case.
  4. Mapped confirmed activity to ~20 MITRE ATT&CK techniques to reconstruct the attack narrative rather than treat each alert in isolation.
Key challenge

Alert volume, not detection, was the real bottleneck — early correlation searches surfaced far more noise than signal. The actual work was building a consistent triage rubric and refining search logic until the alert queue was reviewable rather than overwhelming.

Outcome

A documented, evidence-backed timeline for each simulated attack chain, plus a repeatable triage process I could hand off to another analyst.

CASE-02 · DETECTION-ENGvalidated

Detection Engineering & Threat Simulation

Proving detection coverage instead of assuming it.

Objective

A detection rule that's never been tested against real technique execution is a guess, not a control. I wanted to validate coverage the way a purple team would — attack first, then check what actually fired.

Approach
  1. Used Atomic Red Team to safely emulate specific techniques across credential access, lateral movement, and privilege escalation in an isolated lab.
  2. Authored 20 Sigma rules targeting the underlying behavior of each technique, written to generalize across variants rather than match one specific indicator.
  3. Ran 30 Atomic Red Team test cases against the rule set and logged true/false positive results for each.
  4. Iterated on rule logic wherever a technique was missed or over-triggered before calling that coverage area validated.
Key challenge

Writing rules in vendor-agnostic Sigma format — rather than hard-coding to one SIEM's query syntax — meant thinking in terms of behavior patterns first and translating second, which is a slower but more durable way to build detection content.

Outcome

A documented rule set with pass/fail results per technique, and a repeatable emulation-to-validation workflow.

CASE-03 · MALWARE-CTIanalysis

Malware Analysis & Cyber Threat Intelligence

From a raw sample to intelligence a SOC can act on.

Objective

Detection rules and IOCs are only as good as the analysis behind them. I wanted to practice the full pipeline: take an unknown sample and turn it into something a SOC team could actually use for detection tuning.

Approach
  1. Ran initial static analysis (PEStudio, VirusTotal) on 15–20 samples to fingerprint file characteristics, imports, and known signatures before executing anything.
  2. Detonated samples in an isolated REMnux/FLARE VM environment to observe runtime behavior — network callbacks, file and registry changes, persistence mechanisms.
  3. Extracted IOCs (hashes, IPs/domains, mutexes) and mapped observed behavior to MITRE ATT&CK techniques.
  4. Documented findings per sample in a short analysis writeup, formatted the way I'd hand it to a SOC team for detection tuning.
Key challenge

Deciding how deep to go on each sample. Static analysis alone was enough to triage clearly commodity malware, but anything packed or evasive needed full dynamic detonation — learning to make that call quickly was as much a part of the skill as the analysis itself.

Outcome

A working malware triage workflow and a consolidated IOC set usable for detection rule tuning.

CASE-04 · IDENTITY-SEChardening

Active Directory Security & Identity Management

Hardening the identity layer attackers actually use.

Objective

Most attack paths run through identity, not the perimeter. I built and hardened an AD environment from scratch to practice the access-control decisions that usually get skipped in a lab that's just "AD that works."

Approach
  1. Built out Windows Server and Active Directory from scratch, including DNS, DHCP, OU structure, and Group Policy.
  2. Applied least-privilege access design through RBAC and GPO rather than defaulting to flat, broad permissions.
  3. Used PowerShell to script routine identity management tasks — provisioning, permission audits — instead of doing them manually.
Key challenge

Modeling the OU and permission structure around common AD attack paths — for example, avoiding unnecessary domain admin usage for routine tasks — so the environment reflected real hardening decisions rather than just a functioning directory.

Outcome

A hardened AD environment with documented configuration rationale for each major access-control decision.
